## 0. この手順書の位置づけ

- **Notion連携ができるまでの暫定手順**です。現在は、サイトの内容（ヒーロー・テキスト・SNS・作品・ニュース）を**このリポジトリ内のファイルを直接編集**して更新します。
- Notion連携の完成後は、**作品・ニュースはNotion側で管理**する予定です（Notionで入力 → 自動でサイトに反映）。その時点で本手順書の「作品」「ニュース」の章は使わなくなり、手順書を改訂します。ヒーロー・SNS等のサイト設定をどこで管理するかは、連携の設計時に決めます。
- 反映先は現在、**検証環境（`dev.asnomi.com`）のみ**です。本番（`asnomi.com`）への反映手順は、本番環境の構築後に追記します。

## 1. はじめに：公開リポジトリでの注意（必ず読む）

このリポジトリは **Public（誰でも閲覧可能）** です。次の点を守ってください。

### 1.1 更新できる人・できない人

| | できること |
| --- | --- |
| リポジトリのオーナー（書き込み権限を持つ人） | ファイルの変更・PRの作成・PRのマージ（＝サイトへの反映） |
| それ以外の人（誰でも） | ファイルの閲覧、コピー（fork）、**変更の提案（PR）まで**。マージはできないので、サイトは変わらない |

- サイトに反映されるのは **`dev` ブランチに取り込まれたとき（マージ・push）だけ**です。外部の人のPRが届いても、オーナーがマージしない限りサイトは変わりません。
- **知らない人からのPRはマージしない**でください。内容を確認せずにマージすると、サイトを書き換えられたり、自動デプロイの仕組み（`.github/workflows/` 配下や `package.json` 等）を変更されたりするおそれがあります。
- 書き込み権限（Collaborator）を他の人に付与する場合は、信頼できる人に限ってください。

### 1.2 リポジトリに書いてはいけないもの

ファイルの中身だけでなく、**コミットの履歴も誰でも見られます。後からファイルを消しても、過去の履歴には残ります。**

- パスワード、APIキー、アクセストークン等の秘密情報
- 公開したくない個人情報（住所・電話番号・本名など）や、非公開の資料・メモの内容・保存場所
- 写真の位置情報: スマホ等で撮った写真には撮影場所（GPS）の情報が埋め込まれていることがあります。**写真を追加する前に位置情報を削除**してください（ビルド時に変換される画像からは消えますが、元ファイルはリポジトリにそのまま残るため）。

### 1.3 推奨設定（未設定・要対応）

現在、`dev`・`main` ブランチの保護設定がありません（オーナー自身が誤って直接 push できてしまう状態）。GitHub の **Settings → Rules → Rulesets** で、次の設定を推奨します。

- `dev`・`main` への変更は **PR経由のみ**に限定する（直接 push を禁止）
- ブランチの **強制上書き（force push）と削除を禁止**する

（1人で運用している間は「レビュー承認必須」は付けないでください。自分のPRを自分で承認できず、マージできなくなります。）

## 2. 更新の全体の流れ

```
① 作業用ブランチを作る（dev から）
② ファイルを編集する（本手順書 3〜5章）
③ 手元で表示を確認する（6章） ※省略可。ただし画像やレイアウトを変えたときは推奨
④ コミットして GitHub に push する
⑤ dev 宛てに PR を作り、差分を確認してマージする
⑥ 自動デプロイ（数分）→ dev.asnomi.com で確認する
```

### 2.1 コマンドで行う場合

作業はリポジトリのルートフォルダで行います。ブランチ名は `feature/` で始め、内容が分かる英語にします（例: `feature/content-news-202611`）。

```bash
git checkout dev
```

```bash
git pull origin dev
```

```bash
git checkout -b feature/content-news-202611
```

ファイルを編集したら、コミットして push します。

```bash
git add -A
```

```bash
git commit -m "ニュースを追加: 〇〇のお知らせ"
```

```bash
git push -u origin feature/content-news-202611
```

```bash
gh pr create --base dev --title "ニュースを追加: 〇〇のお知らせ" --body "ニュース1件を追加"
```

GitHub の PR 画面で **「Files changed」タブの差分を確認**し、問題なければ **Merge** します。

### 2.2 ブラウザ（GitHub上）だけで行う場合

テキストの修正程度なら、GitHub の画面だけで完結できます。

1. GitHub でリポジトリを開き、ブランチを `dev` に切り替える
2. 編集したいファイルを開き、右上の鉛筆アイコン（Edit）を押して編集する
   - 画像を追加する場合は、追加先のフォルダを開いて **Add file → Upload files**
3. 「Commit changes」で **Create a new branch for this commit and start a pull request** を選ぶ（`dev` に直接コミットしない）
4. 作成されたPRの差分を確認して **Merge**

### 2.3 反映の確認

- マージすると、GitHub の **Actions** タブで `deploy-dev` が動きます（数分）。緑のチェックになれば完了です。
- `https://dev.asnomi.com/` を開いて確認します。表示が変わらない場合は、ブラウザの強制再読み込み（Windows: `Ctrl+F5`、Mac: `Cmd+Shift+R`）を試してください。
- 赤い×（失敗）になった場合は 7章を参照してください。**失敗した場合、サイトは更新前の状態のまま**です（壊れた状態で公開されることはありません）。

### 3.1 ヒーロー・トップの紹介文（`content/_index.md`）

```yaml
banner:
  image : "images/hero/hero.jpg"
  title : ""        # キャッチコピー。改行したい位置に <br> を入れる。空なら非表示
  subtitle : ""     # サブテキスト。空なら非表示

about:
  enable : true
  content : "趣味でイラストレーター/シンガーソングライターしてる…"
  button:
    enable : true
    label : "プロフィールを見る"
    URL : "about"
```

### 3.2 SNSリンク（`config/_default/params.toml`）

上から順に、ヒーロー（アイコン）とお問い合わせページ（アイコン＋名前）に表示されます。

```toml
[[social]]
title = "Instagram"                          # 表示名
link = "https://www.instagram.com/xxxx/"     # リンク先URL
icon = "ti-instagram"                        # アイコン（Themifyアイコンのクラス名）

[[social]]
title = "SoundCloud"
link = "https://soundcloud.com/xxxx"
badge = "SC"                                 # アイコンが無いサービスは丸囲みの文字で表示
```

- アイコンは [Themify Icons](https://themify.me/themify-icons) の一覧にあるもの（`ti-instagram`・`ti-youtube` 等）が使えます。無いサービスは `icon` の代わりに `badge`（1〜2文字程度）を書きます。
- 削除はブロックごと消す、並べ替えはブロックの順番を入れ替えるだけです。

## 4. 作品の追加・修正

### 4.1 ファイルの作り方

`content/works/` に、**半角英数字のファイル名**で `.md` ファイルを1つ作ります。ファイル名がそのままURLになります（例: `hyouhon1422.md` → `/works/hyouhon1422/`）。

```markdown
---
title: "ヒョウホン1422"
date: 2025-04-27
image: "images/works/hyouhon1422.png"
categories: ["楽曲"]
description: "作品の説明文。作品詳細ページの冒頭に表示されます。"
draft: false
---

（任意）作品詳細ページに載せる本文。省略可。
```

| 項目 | 内容 |
| --- | --- |
| `title` | 作品名 |
| `date` | 頒布日。一覧は新しい順に並ぶ（日付の書き方は 5.2） |
| `image` | 作品画像のパス（書き方は 4.2） |
| `categories` | ジャンル。作品ギャラリーの絞り込みボタンになる。複数可（例: `["楽曲", "イラスト"]`）。**表記を揃える**こと（「同人誌」と「同人本」は別ジャンル扱いになる） |
| `description` | 説明文 |
| `price` | （任意）価格。数字のみ（例: `800`）。「800円」と表示され、`0` は「無料」と表示される |
| `spec` | （任意）仕様（例: `"A5 フルカラー 28ページ"`） |
| `shops` | （任意）販売先のURL。`booth` `melonbooks` `streaming` の3つ（下の例） |
| `sale_status` | （任意）`"販売中"` か `"販売終了"`。販売終了にすると販売先ボタンは出ず「販売終了」と表示。販売中でURLが無ければ「イベント・直販のみ」と表示 |
| `draft` | `true` にすると非公開（下書き） |

```yaml
shops:
  booth: "https://xxxx.booth.pm/items/0000000"
  streaming: "https://..."
```

**本文（任意）**: `---` の下に Markdown で書けます。YouTube動画は `{{< youtube 動画ID >}}` と書くと埋め込めます（押すまで動画を読み込まない軽い表示）。見出し（`## 見出し`）、段落、リンク（`[表示文字](URL)`）、画像等が使えます。本文に載せる画像の書き方は、4.2の「本文中の画像」を参照してください。

### 4.2 画像の置き場所とパスの書き方

- 画像ファイルは **`asnomi-kross-mock/assets/images/` の下**に置きます（作品は `assets/images/works/`）。
- front matter（`---` で囲まれた部分）にパスを書くときは、**先頭の `assets/` を付けずに** `images/works/xxx.jpg` と書きます。
- `assets/` に置いた画像は、ビルド時に自動でサイズ調整・WebP変換されます（元画像が大きくても表示は軽くなります）。
- ファイル名は**半角英数字・ハイフン**にしてください（日本語・空白は避ける）。
- 目安: 作品画像は長辺 800〜2000px、ヒーロー画像は 2400×1350px 前後（16:9）。1ファイル数MB程度まで。
  - リポジトリの履歴に残り続けるため、極端に大きいファイル（数十MB）は避けてください。
- 位置情報の削除を忘れずに（1.2）。

**本文中の画像（作品詳細・ニュースの本文に Markdown で載せる画像）も、置き場所と書き方は同じです。**

- 画像は **`asnomi-kross-mock/assets/images/` の下**に置き（例: `assets/images/works/hyouhon1422-1.jpg`）、本文には**先頭の `assets/` を付けずに** `images/...` と書きます。

```markdown
![ジャケット裏面](images/works/hyouhon1422-1.jpg)
```

- 本文の画像も自動でサイズ調整・WebP変換されます。本文の幅より大きい画像は幅に収まるよう縮小されます。
- 先頭に `/` を付けたり（`/images/...`）、`static/` に置いたりすると、この自動処理の対象外になります。特別な理由が無ければ `assets/` に置いてください。
- Notion連携後は、Notionのページ本文に貼った画像が同期時に自動で `assets/images/` に保存され、この形で書き出されます。手で置く必要はありません。

## 5. ニュースの追加・修正

### 5.1 ファイルの作り方

`content/news/` に `.md` ファイルを作ります。ファイル名は `日付-内容` の形（半角英数字）にすると整理しやすいです（例: `2026-11-exhibition.md`）。

```markdown
---
title: "〇〇に出展します"
date: 2026-11-10
description: "一覧・SNS共有時に使われる短い説明。"
draft: false
---

本文をここに書きます。URLはそのまま書けば自動でリンクになります。 https://example.com

段落を分けるときは、空行を1行入れます。
```

- トップページの「お知らせ・近況」には、**新しい順に3件**表示されます。
- 画像を付けたい場合は `image: "images/news/xxx.jpg"` を追加し、`assets/images/news/` に画像を置きます（無くても可）。

### 5.2 日付の書き方と公開タイミング

- `date: 2026-11-10` のように日付だけ書けば、**日本時間のその日の0時**として扱われます。時刻まで指定する場合は `2026-11-10T18:00:00+09:00` と書きます。
- **未来の日付の記事は公開されません**（その日時を過ぎてから行われたデプロイで初めて表示されます）。予約投稿のように使えますが、現在は**定期的な自動デプロイが無い**ため、日付を過ぎた後に何らかの更新（PRのマージ）が必要です。
  - 定期的な自動デプロイは、Notion連携と合わせて導入予定です。

## 6. 手元で表示を確認する（任意）

初回のみ、Hugo（v0.152.2 extended）・Go・Node.js のインストールが必要です。

### 6.1 通常の確認（推奨）

```bash
cd asnomi-kross-mock
```

```bash
hugo server
```

ブラウザで `http://localhost:1313/` を開きます。ファイルを保存すると自動で表示が更新されます。終了は `Ctrl+C` です。

- 未来日付の記事も表示して確認したい場合は `hugo server --buildFuture` で起動します。

### 6.2 公開時と同じ状態での確認（見た目を大きく変えたとき）

公開時は未使用のCSSを自動で削除する処理（PurgeCSS）が動きますが、6.1の確認ではこの処理が動きません。テンプレートやデザインを変更したときは、次の方法でも確認してください（初回は `npm ci` が必要）。

```bash
npm ci
```

```bash
HUGO_ENVIRONMENT=production hugo server -e production
```

（Windows の PowerShell の場合は `$env:HUGO_ENVIRONMENT="production"; hugo server -e production`）

## 7. うまくいかないとき

| 症状 | 確認すること |
| --- | --- |
| Actions の `deploy-dev` が赤い×になった | Actions タブで失敗したジョブを開き、`Hugo build` のログを見る。front matter の書き間違い（`"` の閉じ忘れ、インデントずれ、全角スペース）が多い |
| 画像が表示されない | パスの先頭に `assets/` を付けていないか、ファイル名の大文字・小文字・拡張子が一致しているか |
| 記事が表示されない | `draft: true` になっていないか、日付が未来になっていないか |
| ジャンルボタンが増えた・分かれた | `categories` の表記ゆれ（全角/半角、表記の違い） |
| 反映したが表示が変わらない | 強制再読み込み。それでも変わらなければ Actions が完了しているか確認 |

### 7.1 元に戻したいとき

マージ済みのPRを開き、**Revert** ボタンを押すと「その変更を取り消すPR」が作られます。それをマージすれば元の状態に戻ります。
